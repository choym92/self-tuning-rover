# 13 — Unitree G1 Security Disaster
- 한 줄 요약: 커뮤니티가 발견한 Unitree 로봇 전 기종 공통 BLE 취약점(하드코딩된 AES 키)을 실제 Jeff(G1)에 라이브로 재현해 root 권한 원격 코드 실행과 무단 텔레메트리 전송을 입증하고, Unitree의 공식 해명을 조목조목 반박하는 영상.
- 로봇 관련성: 중간 (RL/센서/액추에이터 개발이 아니라 보안·네트워킹 이슈이지만, G1의 보드 구성과 하드웨어 통신 구조를 이해하는 데는 유용함)

## 하드웨어
- G1의 메인보드(main board): 소유자에게 root/shell 접근 권한이 전혀 없는 proprietary 보드. EDU 버전에는 별도의 secondary 보드가 추가됨.
- 메인보드에는 상시 켜져 있는 Bluetooth Low Energy(BLE)가 있으며, 소유자가 끌 수 있는 방법이 없음.
- LiDAR는 완전히 별도의 자체 컴퓨터로 동작. RealSense(depth 카메라)는 (본인 추정상) Jetson 보드에 연결되어 있다고 언급(불확실).
- 취약점 발생 계열: G1, H1, Go(옵션 명확X), B2, R1 등 Unitree 로봇 전 기종이 동일한 하드코딩 AES 키를 공유.

## 소프트웨어 스택
- 커뮤니티 제작 공격 도구: 자막상 "Unione"/"uni pone"으로 반복 표기되나 실제 프로젝트명은 불명확(파이썬 스크립트, GitHub 공개, hack.py/wifi_update.py 등으로 구성). 공식 리포지토리 규모는 작다고 언급.
- sentdex 본인은 이 툴의 APK는 실행하지 않고, 코드를 직접 읽고 재구현/재사용하는 방식으로 검증.
- 자체 access point 구성에 Linux 네트워킹 도구(hostapd류 추정, 자막엔 구체적 명령어만 나열) + tcpdump/tshark로 트래픽 모니터링.
- pcap 분석에 "codeex and 03"(추정: OpenAI Codex/o3)의 도움을 받아 트래픽량(속도) 계산.
- 참고 문헌: 제3자 보안 논문(저자/제목 자막에 없음)에서 원격코드실행 및 텔레메트리 관련 주장을 제기했고, 이 영상은 그 주장을 직접 재현/검증.

## 만드는 과정 — 순서대로
1. (배경) 약 1년 전 "원격 어디서든 코드 실행 가능"이라는 더 심각한 주장이 있었으나 증거를 찾을 수 없었고 Unitree는 과장이라 주장 — sentdex는 이번엔 직접 증거를 만들겠다고 선언.
2. G1(Jeff)을 배터리만 넣고 이더넷 미연결 상태로 부팅 — "로봇이 네트워크와 전혀 연결되지 않은 상태"임을 카메라로 명시적으로 보여줌.
3. 리모컨으로 로봇을 세운 뒤(리모컨은 이후 끔), 커뮤니티 스크립트(hack.py)의 reboot 플래그로 BLE를 통해 Wi-Fi 자격증명 필드에 명령어를 주입 → 실행.
4. 몇 초~10~15초 후 로봇이 실제로 재부팅됨을 확인(딸깍 소리, 팔이 축 처짐, 재부팅 시퀀스) → 순수 BLE만으로 root 권한 원격 코드 실행이 실제로 가능함을 입증.
5. 다음으로 텔레메트리(허락 없는 인터넷 전송) 주장을 검증하기 위해, 자신의 Wi-Fi 카드를 access point("sentNet")로 만들고 인터넷 업링크 연결.
6. BLE 취약점을 이용해 G1의 Wi-Fi 자격증명을 자신이 만든 access point로 강제 변경(로봇에게 "연결하라"고 명시적으로 요청한 적은 없고 그냥 자격증명만 갱신).
7. tcpdump/tshark로 access point 트래픽을 실시간 모니터링 → 로봇이 전원이 들어오자마자 자동으로 연결하고 다수의 시리얼넘버 조회, DNS 조회(MQTT 서버로 추정)를 시작하며 지속적으로 통신하는 것을 시연.
8. 두 개의 IP 주소로 나가는 트래픽량을 측정(자신의 실측치는 제3자 논문의 주장치보다 훨씬 작음, 약 0.01Mbps ≈ 분당 1.4MB) — 논문 주장(약 1.4Mbps)과 차이가 큼을 지적, 펌웨어/지역차 가능성 언급하되 확답은 못함.
9. Unitree의 공식 입장문을 화면에 띄우고 한 문장씩 반박: "기본적으로 오프라인/미연결"이라는 문구를 로봇을 재부팅해 즉시 통신이 시작되는 걸 보여주며 반박, "설정(setup)"과 "인가(authorize)"를 구분해 쓰는 것에 대해서도 반박(공식 앱 온보딩 1단계가 바로 Wi-Fi 자격증명 등록임을 근거로).

## 막힌 곳과 해결법
- 처음엔 논문의 injection 방식을 그대로 구현했으나 동작하지 않아 "패치됐나보다" 생각했다가, 이후 다시 시도해 성공(패치되지 않았음을 재확인) — 원인은 명시되지 않음, 커뮤니티 툴의 명령 주입 방식이 논문과 "약간 다르다"는 점만 언급.
- pcap 분석에 익숙하지 않아(본인 왈 "wireshark 설치도 이번에 처음 해봄") LLM(Codex/o3)의 도움을 받아 트래픽량을 계산.
- 관찰된 데이터 전송량이 참조 논문의 수치와 상당히 다름(더 적게 관측) — 원인 불명, 본인도 "잘 모르겠다"고 인정, 시청자에게 의견을 구함.
- 취약점에 대한 실질적 방어책이 마땅치 않음: 하드코딩된 AES 키가 패치되지 않는 한 근본 해결 불가. 본인의 임시 대응은 배터리를 항상 빼두고 이더넷을 항상 뽑아두는 것(Wake-on-LAN/PoE 우려 때문), 그리고 root 권한을 얻은 뒤 Bluetooth를 직접 비활성화하거나 물리적으로 desolder하는 것 정도만 대안으로 제시(둘 다 확실한 해결책은 아님).

## 수업 개념과 연결
없음 — 이 영상은 보안/네트워킹 주제로, KF/PF/PID/SLAM 등 수업에서 다루는 알고리즘과의 연결점은 없음.

## Paul의 Hardware Challenge에 주는 교훈
- Paul이 검토 중인 Freenove/XGO-mini2는 Unitree G1과 무관한 하드웨어이므로 이 BLE 취약점 자체는 직접 해당 없음 — 다만 저가/중국산 IoT형 로봇 하드웨어 전반에 "하드코딩된 인증키"류 보안 이슈가 흔할 수 있다는 일반적 경각심은 참고할 만함.
- 개발 중인 로봇/보드를 인터넷에 상시 연결해두지 않는 습관(배터리 분리, 이더넷 미연결)은 하드웨어 챌린지 개발 중에도 적용할 만한 좋은 기본 위생 수칙.
- 만약 Jetson 보드에 Wi-Fi/BLE를 켜둔 채로 개발한다면, 기본 자격증명이나 열린 포트를 방치하지 않도록 점검하는 습관이 필요.
- (직접적 교훈이라기보다) 이 영상은 하드웨어 선택보다는 "완제품 로봇 플랫폼을 쓸 때 공급망/보안 리스크를 어떻게 평가할지"에 대한 참고 사례 정도로 이해하면 됨 — Hardware Challenge 자체의 알고리즘/설계 의사결정에는 크게 영향 없음.

## 확인 필요
- 공격 도구의 정확한 프로젝트명(자막엔 "Unione"/"uni pone"으로만 나옴, 실제 명칭 불명확).
- 참조된 제3자 보안 논문의 저자/제목이 영상에서 명시되지 않아 확인 불가.
- 트래픽량 수치("39메가비트", "1.4메가비트", "0.01메가비트" 등)가 자막상 여러 차례 뒤섞여 나와(예: "1.4 24 megabits per second") 정확한 값 단정 어려움 — 대략적 경향(본인 실측치가 논문 주장치보다 작다)만 신뢰할 수 있음.
- RealSense가 정확히 어느 보드(Jetson)에 연결되어 있는지는 본인도 "기억이 안 난다"고 말함 — 불확실.
- LiDAR가 "완전히 별도의 컴퓨터"라는 설명의 세부 구조(어떤 SoC인지 등)는 언급되지 않음.
