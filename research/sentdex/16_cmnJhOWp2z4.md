# 16 — A bigger brain for the Unitree G1 (P.4)

- 한 줄 요약: 소형 VLM(Moondream2)로 자연어 기반 물체 탐지·좌표추출을 붙여 손-물체 추적 프로토타입을 만들었지만, 오른손이 물리적으로 고장났고 카메라 시야각 한계·IK/경로계획 필요성이라는 구조적 문제를 명확히 짚어낸 회고형 영상.
- 로봇 관련성: 높음

## 하드웨어 (robot, sensors, actuators, compute board, prices if stated)
- **오른손(Dex3) 하드웨어 고장 발견**: 왼손은 정상 작동하는데 오른손만 명령에 반응 안 함 → 포트를 바꿔보고(좌/우 포트 교체), 후면 커버를 열어 열화상 카메라로 확인한 결과 오른손에만 전원이 전혀 안 들어옴(열이 없음)을 확인 — 물리적 고장으로 결론. 영상 17에서 학습한 팔 정책이 하필 오른팔용이라 타격이 큼.
- Inspire 손으로 교체를 고려했으나, 매뉴얼 확인 결과 별도 어댑터 보드가 필요하다는 것을 알게 됨 → 현재 보유하지 않아 RoboStore에 요청, 아직 미수령.
- 후면 커버를 열어본 내부 모습이 "노트북 같다"는 반응(시청자 댓글 인용) — 소형화를 위해 노트북급 부품/열관리 기술을 쓴 것으로 추정. 후면 커버를 뗀(냉각에 더 불리한) 상태에서도, 약 5분간 걷기+SLAM 등 부하를 준 뒤 측정한 열화상 상 각 부품 온도는 정상 범위로 보임 — 과열 우려는 크지 않다고 평가.
- Jetson 보드 RAM: "16GB 또는 32GB"라고 언급하나 본인도 정확한 스펙을 확신 못함(불확실).
- 카메라 배치 문제: 머리에 있는 RGB/뎁스 카메라가 아래를 보면 조리대 위 물체는 보이지만 손은 안 보이고, 반대로 뒤로 젖혀 앞을 보면 조리대는 보이지만 손이 안 보여 손-물체 동시 추적이 어려움. 이상적으로는 카메라 2개(전체 시야용 + 그리퍼 근처용)가 필요하다고 결론.

## 소프트웨어 스택 (OS, SDKs, frameworks, models, languages, sim tools)
- VLM: **Moondream2** — 약 20억(2B) 파라미터 미만, 메모리 약 5GB. 양자화(quantized) 버전도 있지만 point(좌표점) 출력 모드를 지원하지 않아 이번 용도에는 부적합, 게다가 point 모드와 bounding box(object detection) 모드 간 정확도 차이도 있다고 관찰(경험상 point가 더 정확했다고 언급).
- Moondream 기능: short caption, (normal/long) caption, query(VQA), object detection(bounding box), point(좌표점) — GUI(Codex/o3로 제작)로 각 기능을 시연.
- 자연어 기반 open-vocabulary 탐지 데모: "red bottle of water" vs "yellow bottle of water" 구분(단, 한 케이스에서 point는 맞았지만 object detection은 틀림), sink, microwave, "음식을 데우는 장치"(추상적 설명으로도 전자레인지 인식 성공), canned air 등.
- 이번 영상에서 Claude 4가 막 출시됐다는 언급 — 향후 시리즈에서 사용 모델을 바꿀지 고려 중이라고만 언급, 아직 사용은 안 함.
- 향후 파이프라인 구상: 자연어 명령 → function calling으로 목적지+타겟 물체 추출 → 이동(로코모션+SLAM/occupancy grid, 이전 영상 스택) → VLM으로 물체·손 좌표 추적(빨간 십자=손, 노란 십자=목표 물체) → 팔 정책으로 이동.

## 만드는 과정 — 순서대로 (what he tried first, next, ... in chronological order; the actual workflow)
1. 먼저 Dex3 손의 grab(쥐기) 기능을 프로그래밍하려다 계속 실패 → 디버깅 삼아 왼손으로 바꿔 테스트했더니 바로 성공 → 오른손 고장을 의심.
2. 포트 교체(좌/우 포트 바꿔 연결), 상/하단 포트 옵션 테스트 등으로 원인 격리 시도 → 안 됨.
3. 후면 커버를 열고 열화상 카메라로 확인 → 오른손에 전원이 전혀 안 들어옴을 확인, 물리적 고장으로 결론.
4. Inspire 손 교체를 검토했으나 어댑터 보드 필요 사실을 매뉴얼에서 발견 → 현재 보유하지 않아 요청만 해둔 상태로 보류.
5. VLM(Moondream2) 기반 GUI를 만들어 caption/query/detection/point 기능을 시연하며 open-vocabulary 물체 인식 가능성 확인.
6. 손(black robotic hand)과 목표 물체(예: graphics card)를 동시에 VLM으로 추적하는 프로토타입 시연 — 빨간 십자(손), 노란 십자(목표) 표시, 손이 목표를 향해 매우 천천히(안전을 위해 의도적으로 느리게) 이동.
7. 카메라 시야각 문제(손 vs 주변 환경을 동시에 볼 수 없음)와 depth 기준점 문제(머리 카메라 기준 깊이 vs 손 기준 깊이가 다름)를 분석 — 이상적으로는 그리퍼 근처에 별도 카메라 필요하다고 결론.
8. "사이드 퀘스트"로 머리를 뒤로 25도 기울여 카메라가 조리대를 보게 하면 SLAM/occupancy grid가 어떻게 되는지 실험 — 이 각도 보정 없이 그냥 틀면 occupancy grid가 완전히 "포화(saturated)"되어 오작동.
9. 환경변수로 LiDAR/head tilt 각도(25도)를 명시적으로 지정해 SLAM/occupancy grid 계산에 보정 적용 → 눈에 띄게 개선되었지만 일부 구역은 여전히 부정확(실제 각도가 25도가 아니라 23도 근처일 수 있다고 추정), 걷는 동안 머리가 흔들려 생기는 노이즈도 원인으로 지목.
10. 다음 단계로 IK(inverse kinematics, "코스 알고리즘"이 아니라 영상 내 화두)를 팔 정책 개선에 적용할지 고민, 동시에 "IK만으로는 장애물을 피해 갈 수 없다"는 점에서 별도의 경로계획(path planning)도 필요함을 결론지으며 영상 마무리.

## 막힌 곳과 해결법 (failures, bugs, surprises, and how he debugged or worked around them)
- **오른손 완전 고장** — 좌/우 손 교체 테스트, 포트 교체 테스트, 열화상 카메라로 전원 미공급 확인 후 "물리적 고장"으로 결론. 해결책(수리/교체)은 아직 없음(RoboStore 응답 대기, 미해결).
- **Inspire 손으로 대체하려 했으나 어댑터 보드가 없어서 불가능** — 매뉴얼을 보고서야 알게 된 요건, 현재 미해결.
- **머리를 뒤로 기울이면 SLAM/occupancy grid가 깨짐** — 기존 파이프라인이 기본(아래를 보는) 머리 각도를 가정하고 만들어졌기 때문 → 알려진 기울기 각도(25도)를 하드코딩해 좌표 변환을 보정하는 방식으로 상당 부분 해결했지만 완전하지는 않음(잔여 오차, 정확한 각도 미확정, 걷는 동안의 head bobble도 원인으로 지목).
- **VLM이 종종 손을 오탐지**(예: 삼각대를 손으로 착각) — 해결책으로 손에 색깔 테이프를 감아 구분성을 높이는 방법을 제안(직접 시도는 아직 안 함).
- **파이프라인 전체 프레임레이트가 느림(초당 0.5~1프레임)** — VLM 자체 추론 속도(약 150ms)는 빠른데 전체 파이프라인이 최적화가 안 돼서 느림, 최적화 여지가 있다고만 언급(구체적 해결 미시행).
- **깊이 기준점 불일치(머리 카메라 vs 손)** — 동일 깊이에 있는 두 물체가 머리 카메라 기준으로는 다른 깊이로 잘못 인식되는 문제, 근본 해결책(그리퍼 카메라 추가 또는 삼각법 계산)은 다음 단계 과제로 남김(미해결, 구상만 제시).

## 수업 개념과 연결 (any link to KF / PF / PID / SLAM / localization / path planning / control loops / RL; write "없음" if none — do not invent links)
- **Path planning / Search**: 명시적으로 "IK만으로는 장애물(예: 병 옆의 바(bar))을 피해갈 수 없어 별도의 경로계획이 필요하다"고 스스로 정리함 — 수업의 search+smoothing 주제와 개념적으로 직접 연결되는 좋은 사례(단, 실제 알고리즘 구현은 없음, 필요성만 논의).
- **Inverse Kinematics(IK)**: "팔 동작을 더 자연스럽게 만들기 위해 IK를 시도해볼까 고민 중"이라고 언급 — 아직 구현 전, 개념적 논의 단계. IK는 course의 필수 5개 알고리즘(KF/PF/PID/SLAM/search) 목록엔 없지만 로봇 팔 제어 맥락에서 자주 함께 언급되는 인접 개념.
- **Localization/좌표변환**: 머리 기울기(25도)에 따른 LiDAR/SLAM 좌표 보정 작업은 센서 기준 좌표계를 로봇/월드 좌표계로 변환하는 캘리브레이션 사례 — 필터링(KF/PF)은 아니지만 좌표계 정합이라는 인접 주제.
- **RL/Sim-to-real**: 보행/댄스처럼 고유감각(proprioceptive) 데이터만 필요한 과제는 시뮬레이션이 상대적으로 쉽지만, 카메라·뎁스·LiDAR 같은 센서 데이터를 포함하는 조작(manipulation) 과제는 시뮬레이션-실물 간 센서 정합이 어려워 sim-to-real이 훨씬 어렵다는 견해를 재차 밝힘(영상 17과 일관됨) — 구현이 아닌 의견 진술.
- **PID/KF/PF**: 명시적 구현이나 언급 없음.

## Paul의 Hardware Challenge에 주는 교훈 (concrete, 2–5 bullets)
- **카메라 등 센서 배치는 "동시에 볼 수 있는 것"의 한계를 고려해 설계할 것** — 손과 주변 환경을 한 카메라로 동시에 보기 어렵다는 이 사례처럼, Paul의 조작(manipulation) 과제가 있다면 센서 위치를 미리 시뮬레이션/스케치해볼 것.
- **하드웨어는 프로젝트 중간에 고장날 수 있다** — 오른손 사망처럼, 데드라인(2026-12-10) 전에 예비 부품이나 축소된 데모 시나리오(fallback)를 마련해둘 것. 새 장비는 가능한 한 일찍 통전/기능 테스트를 해서 초기 불량을 조기에 발견할 것.
- **센서를 기본 자세에서 바꾸면(예: 각도 조정) 반드시 좌표변환/캘리브레이션 코드를 함께 갱신해야 함** — 머리를 25도 기울였을 때 occupancy grid가 깨진 사례가 직접적인 반례.
- **오픈보캐뷸러리 VLM(Moondream2, ~2B, ~5GB)은 소형 보드에서도 돌아갈 만큼 가볍다** — Paul이 고수준 물체 인식(예: "이건 무엇이다")에 VLM을 보조적으로 쓰고 저수준 제어는 코스 알고리즘(KF/PF/PID/SLAM/search 중 하나)으로 구현하는 조합을 고려할 수 있음. 다만 VLM 사용 자체는 과제 요건(코스 알고리즘 구현)을 대체하지 못한다는 점을 유의.
- **IK와 경로계획(path planning)은 별개 문제**라는 sentdex의 명확한 정리는, Paul이 로봇팔 관련 과제를 고를 경우 "장애물 회피"를 위해 search/smoothing 같은 별도 레이어가 필요하다는 점을 스스로 되짚어보는 데 유용한 참고점.
