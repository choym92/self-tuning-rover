# 12 — Training a Unitree G1 to Walk w/ Reinforcement Learning
- 한 줄 요약: MJLab(MuJoCo 기반) 시뮬레이터에서 PPO 계열 velocity-tracking 보행(gait) policy를 학습하고, "explicit PD controller로 교체"가 핵심 돌파구였던 sim-to-sim → sim-to-real 전 과정을 트랙터를 이동식 gantry(안전장치)로 활용해 실외에서 실증한, 이 배치에서 가장 핵심적인 RL 워크플로 영상.
- 로봇 관련성: 높음

## 하드웨어
- Unitree G1(Jeff): 다리 전체를 사용하는 보행(gait) policy를 실기에 적용. 어깨 joint의 플라스틱 고정 탭(tab)이 두 번이나 파손되어 팔이 빠지는 사고 발생 — 3D 프린팅 부품 vs 금속 보강 여부를 고민 중(결론 없음, "일부러 희생 부품(sacrificial part)으로 설계됐을 수도 있다"는 가설만 제시).
- 손: 기존 "3-in-1" 핸드에서 Inspire사의 5손가락 핸드로 양손 교체(고장이 아니라 팔이 빠지면서 배선이 뽑혀 어차피 재작업이 필요했던 김에 교체).
- 학습용 GPU: RTX 4090(기준으로 환경 개수를 설정한다고 언급).
- 실외 테스트용 온보드 컴퓨트: **Dell GB10** — Dell이 리뷰용으로 제공, 스펙은 메모리 128GB(저대역폭), 전력 45W, 초소형 폼팩터. 본인 표현으로 "DGX Spark의 Dell 버전이자 Jetson Thor(전 영상에서 다룸)와 비슷한 계열"이라고 설명 — 즉 Jetson Thor / DGX Spark / Dell GB10이 모두 같은 급(128GB 메모리, 약 273GB/s 대역폭, 저전력)의 컴퓨트로 묶임.
- 실외 테스트 리그: 쿠보타(Kubota) 트랙터의 팔레트 포크에 G1을 래칫 스트랩으로 고정해 "이동식 gantry"로 사용(낙상 방지 안전장치). 트랙터 운전석에 USB-C 모니터, 무선 마우스/키보드, GB10을 설치해 현장에서 직접 policy를 조작. 드론으로 공중 촬영도 병행.
- E-stop 방식: GB10이 로봇의 proprietary 메인보드와 Jetson 보드 양쪽에 동시 연결되어 있으며(Jetson 단독으로는 셧다운 명령에 응답이 느림), 이전 영상(13번, Bluetooth exploit)에서 얻은 root 권한으로 메인보드에 강제 종료(hard shutdown) 명령을 보내는 방식을 E-stop으로 사용.

## 소프트웨어 스택
- 시뮬레이터: **MJLab**(MuJoCo/MJ Warp 기반). 다른 사람들이 Unitree G1 sim-to-real에 MJLab을 쓰는 걸 보고 선택. 저자 Kevin Zaka는 공교롭게도 sentdex가 예전에 파이썬을 가르쳤던 "Sentdex 시청자 출신"이라고 언급(친분으로 질문하며 도움받음).
- 대안으로 언급만 된 것: Isaac Lab / Isaac Sim(대규모 인터랙티브 씬 구성 가능하나 물리 스케일링에 한계), Beyond Mimic/Deep Mimic(모션 모방 기반 학습, 이번엔 미사용).
- 학습 전략: MJLab에 내장된 두 예제 중 "motion imitation"이 아니라 **velocity 기반 전략**을 선택(조종 가능한 범용 보행을 원해서). motion imitation은 향후 "쭈그려서 물건 잡기" 같은 동작에 쓸 계획으로 남겨둠.
- LLM 활용: 코드 작성/디버깅에 **Gemini 3 Pro + Gemini CLI**를 광범위하게 사용("이 프로젝트 코드는 사실상 다 LLM이 짠 것"). 에피소드 동적 타임아웃 로직은 Codex/o3가 제안.
- 제어 GUI: 본인이 직접 만든 Python GUI(WASD류 키로 속도 타겟 조작) — sim-to-sim과 sim-to-real, 실제 로봇 제어에 **동일한 코드**를 그대로 사용.

## 만드는 과정 — 순서대로
1. MJLab을 클론해 설치, 데모 실행. 내장 예제 중 velocity 전략 선택(범용 조종형 보행이 목표이므로).
2. 학습 환경 개수 설정(RTX 4090 기준 최대 50,000개 병렬 환경까지 가능, GPU 메모리에 따라 조절). 최종 sim-to-real에 성공한 policy는 약 5,000 iteration, 학습 시간 약 1시간 정도로 상대적으로 빠르게 학습됨(더 큰 30,000~50,000 iteration짜리는 지형 복잡도에 따라 최대 24시간 소요).
3. 기본 설정(velocity 전략, 기본 MJLab PD 컨트롤러)으로 1차 학습 → 결과는 다소 goofy/shuffle한 걸음걸이, 평지/완만한 러프 지형에서는 그럭저럭 균형을 잡지만 계단은 시각 정보가 전혀 없는 "blind gait"라 내려가긴 쉬워도 올라가는 건 각 계단에서 걸려 넘어지며 다음 계단을 붙잡는 식으로만 가능.
4. Sim-to-sim(먼저 시뮬레이터 간 검증)을 시도했으나 반복적으로 실패 — 원인 추적 시작.
5. 원인 디버깅 끝에 **MJLab 기본값인 implicit PD controller**가 문제라고 결론: implicit PD는 시뮬레이터의 "특권적(privileged)" 데이터와 미래 시점 값을 백필해서 계산하는 방식이라 실기에선 재현 불가 → **explicit PD controller**(순수 Python/torch 코드로 계산, 특권 데이터 불필요)로 교체.
6. 교체 직후 sim-to-sim이 처음으로 성공적으로 동작 — 이 순간이 이번 프로젝트의 핵심 돌파구.
7. 또 다른 sim-to-real 갭 요인으로 **linear velocity**를 observation에 포함하는 기본 설정을 지목: 실제 G1은 linear velocity를 직접 측정하는 센서가 없음 → 추정(estimation)을 시도했으나 아직 성공하지 못함(미해결로 남김).
8. sim-to-sim 검증은 MJLab/Isaac Lab API를 거치지 않고 **순수 MuJoCo + 실제 로봇 제어에 쓸 것과 동일한 Python 파이프라인/GUI**로 재실행해 파이프라인 자체의 버그까지 잡아냄.
9. 낙상(fall) 안전장치 추가: 학습 중에는 몸통 각도가 일정 임계값에 도달하면(=쓰러지기 직전) 에피소드를 즉시 종료시키므로, policy는 "바닥에 누운 상태"를 학습 데이터로 본 적이 없음(out-of-distribution) → 실기에서 이 상태에 들어가면 policy가 "정신을 잃은 듯" 이상 동작을 하는 것을 확인 → 해결책으로 몸통 각도/높이가 임계값을 넘으면 policy 출력을 무시하고 강제로 **full damp(전신 힘빼기)** 모드로 전환하는 별도 안전 로직을 추가(policy 자체의 개선이 아니라 감싸는 안전장치).
10. 실기에 처음 policy를 올리자마자 팔이 빠짐(하드웨어 결함/마모 문제로, RL 버그는 아니라고 본인은 판단) → 수리 후 재개.
11. 실외 테스트: 트랙터에 G1을 스트랩으로 고정한 "이동식 gantry" 구성 → 낙엽이 덮인 완만한 경사 콘크리트에서 첫 오프로드 테스트 → 더 가파른 경사 → 마지막으로 경사진 자갈밭까지 난이도를 점진적으로 높임.
12. 각 지형에서 로봇이 휘청여도 스스로 균형을 회복하는 모습을 관찰. 뒤로 걷는 것이 앞으로 걷는 것보다 더 안정적이라고 평가.
13. 자갈/경사 테스트 도중 팔이 두 번째로 빠짐(이번엔 배선까지 뽑힘) → 이 사건을 계기로 야외 테스트 세션 종료, 로봇 "수술"(손 교체 포함 수리) 진행.
14. 사후 분석: 팔을 완전히 고정(freeze)해도 학습된 보행 policy는 여전히 잘 동작한다는 것을 확인 → 균형에 정말 중요한 것은 팔이 아니라 허리(waist)라는 결론. 향후 계획으로 학습 단계에서 팔을 고정하거나 출력에 스무딩을 적용하는 방안을 검토(참고 사례로 G1 복싱 로봇들이 다리는 안정적으로 학습하되 팔/몸통은 외부 충격을 받아들이는 방식으로 설계된다는 점을 언급).
15. Lucky Robots(로보틱스 시뮬레이터 스타트업)에 정규직으로 합류 발표(1년 넘게 자문 역할을 해오다 정규직 전환) — 정규직으로 합류하고 집중한 지 약 3일 만에 그동안 막혀있던 sim-to-real 버그를 해결했다고 언급.
16. Lucky Robots의 목표 설명: (1) 물리 엔진 확장성 문제(MuJoCo/MJ Warp/Newton 계열은 GPU 메모리상 인터랙티브 오브젝트를 다량 넣으면 스케일이 안 됨) 와 (2) 씬(scene) 생성 다양성 문제(Isaac Lab/Sim은 큰 씬은 만들 수 있지만 씬을 직접 제작하는 노력이 여전히 많이 듦)를 동시에 해결하려는 회사. 물리/C++ 엔지니어와 정책(policy) 엔지니어 채용 중이며, 지원자가 만든 policy(예: 물건 잡기)를 실제 G1에서 테스트해주겠다고 제안.
17. 향후 로드맵: 이동(locomotion) policy + 쭈그리기(squat) policy + 팔/그리퍼 policy를 체인으로 연결해 "부엌 가서 물병 집기", "바닥의 장난감을 바구니에 담기" 같은 복합 과제를 수행하는 것이 목표. 후보 기법으로 ACT, Beyond Mimic, "AM/ASE" 계열(자막상 정확한 명칭 불확실, Adversarial Motion Priors/Adversarial Skill Embeddings로 추정) 언급.

## 막힌 곳과 해결법
- **implicit PD controller 문제**: MJLab 기본 PD 컨트롤러가 시뮬레이터 특권 데이터/미래 값에 의존해 실기 재현이 불가능했음 → **explicit(Python/torch로 직접 계산하는) PD controller로 교체**하여 해결. 이 변경이 이번 영상 전체에서 가장 결정적인 돌파구였다고 반복 강조. (다만 여러 로보틱스 전문가들은 "implicit로도 이론상 가능해야 한다"고 말했다며, 본인 경험이 일반적 정답은 아닐 수 있다고 단서를 붙임.)
- **linear velocity 센서 부재**: 실기 G1은 linear velocity를 직접 측정할 수 없어 학습에 쓴 observation과 실기 입력 간 괴리 발생 → 추정(estimator)을 시도했으나 아직 성공하지 못해 미해결 상태로 남김("shuffle" 걸음걸이의 원인으로 의심).
- **out-of-distribution 낙상 상태에서 policy 오작동**: 학습 중 한 번도 보지 못한 "쓰러진 상태"에 실기에서 진입하면 policy 출력이 이상해짐 → policy 자체를 고치지 않고 몸통 각도 임계값 감지 시 강제로 damp 모드로 전환하는 별도 안전 로직으로 우회.
- **실기 첫 로딩 시 팔 빠짐(하드웨어 결함)**: RL 정책 문제가 아니라 어깨 고정 탭의 물리적 마모/파손 문제로 판단, 수리 후 재개. 두 번째로 또 빠졌을 때는 배선까지 뽑혀 손 전체 교체(Inspire 5손가락 핸드)로 이어짐.
- **가파른 경사에서 순간적으로 통제 불능처럼 보였던 구간**: 속도 목표를 0으로 리셋하는 스페이스바 단축키로 겨우 회복 — 완전한 해결책이라기보다는 운전자의 즉각 개입에 의존.
- **어깨 탭 반복 파손**: 근본 원인/재질(플라스틱이 의도된 희생 부품인지, 단순 설계 미흡인지) 불명 → 아직 해결하지 않고 커뮤니티에 자문 구하는 중.

## 수업 개념과 연결
- **PID**: 있음 — sim-to-real 성공의 핵심이 "implicit → explicit PD(Proportional-Derivative) controller 교체"였다는 점은 수업의 PID 개념과 직접적으로 연결됨. 시뮬레이션과 실기의 제어 루프(control loop) 계산 방식을 동일하게 맞추는 것이 policy 자체보다 더 중요했다는 사례.
- **상태 추정(State estimation, KF와 개념적으로 인접)**: 느슨한 연결 — 실제 로봇에 없는 linear velocity를 추정(estimate)해서 보완하려는 시도가 언급되지만, 영상에서 Kalman Filter나 특정 추정 기법을 명시하지는 않음. "센서로 직접 측정할 수 없는 상태 변수를 다른 신호로부터 추정해야 한다"는 문제의식 자체는 KF/state estimation과 맥락이 닿아 있으나, 실제 구현 방법은 나오지 않으므로 직접 인용은 아님.
- **SLAM/PF/경로계획**: 없음 — 이 영상의 보행 policy는 시각 정보 없이 동작하는 "blind gait"이며, 지도 작성이나 위치추정, 경로 스무딩 관련 내용은 전혀 다루지 않음.

## Paul의 Hardware Challenge에 주는 교훈
- Sim-to-real 전에 **sim-to-sim 검증**을 먼저 거치는 습관은, 훨씬 단순한 시스템(예: 센서 하나+액추에이터 하나)이라도 "파이프라인 버그"와 "알고리즘/정책 버그"를 분리하는 데 유용 — Hardware Challenge에서도 시뮬레이션 검증 단계를 넣을 가치가 있음.
- Sim과 실기의 **제어 루프(PD/PID) 계산 방식을 정확히 일치**시키는 것이 정교한 알고리즘보다 더 결정적일 수 있음 — 코스의 PID 프로젝트를 실기에 옮길 때 시뮬레이션 단계의 제어기 구현 디테일(특히 "특권 정보"에 의존하지 않는지)을 반드시 점검할 것.
- 실제로 동작한 신경망은 20만 파라미터 미만으로 매우 작았음 — Hardware Challenge에서 온보드 연산 요구량을 과대평가하지 말 것(저사양 보드로도 충분할 가능성).
- 예측 불가능한/미학습 상태(out-of-distribution)에 대비해 **하드웨어/소프트웨어 차원의 안전장치**(임계값 감지 → 강제 정지)를 반드시 별도로 마련할 것 — 알고리즘을 100% 신뢰하지 않는 설계가 실기 안전에 필수.
- 실외/실물 테스트는 리깅(고정 장치), E-stop 접근성, 역할 분담(운전 vs 제어 vs 관찰) 등 물리적 로지스틱스에 생각보다 많은 준비가 필요함 — 12/10 마감 전 실기 테스트 세션을 위한 시간과 안전장치를 미리 계획해둘 것.

## 확인 필요
- "AM"과 "ASE" 기법 명칭이 자막상 불분명(본인도 "AM이 뭐였는지 순간 까먹었다"고 말함) — 정확히는 Adversarial Motion Priors(AMP), Adversarial Skill Embeddings(ASE)로 추정되나 확정 불가.
- 학습 반복 횟수/시간("50,000개 환경", "5,000/30,000 iteration", "24시간") 은 대략적 진술로, 정확한 실험 로그 기반 수치인지 불확실.
- "Newton"이 물리 엔진의 구체적 프로젝트명을 가리키는지("MJ warp... Newton도 여기 해당될 수도")는 자막이 모호해 특정 짓기 어려움.
- Dell GB10 / DGX Spark / Jetson Thor 세 제품의 관계(같은 세대 칩 기반인지, 정확히 동일 스펙인지)는 본인의 구두 설명에만 근거하며 공식 스펙표 대조는 이뤄지지 않음.
- 어깨 탭이 "의도된 희생 부품"인지 여부는 본인도 결론을 내리지 못한 추측 단계.
