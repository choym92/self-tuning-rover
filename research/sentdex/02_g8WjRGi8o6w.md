# 02 — GLM 5.3 Flash (P.2)
- 한 줄 요약: 이전 영상(05)의 XGO mini 로봇 제어를 규칙 기반(rule-based) 코드에서 GLM 5.3 Flash의 function calling + vision 기반 완전 자율 제어로 전환하는 라이브 코딩/디버깅 영상. 결국 로봇이 스스로 큐브를 찾아 집어드는 데까지 성공.
- 로봇 관련성: 높음 (카메라→VLM 추론→구조화 JSON 출력→SDK 실행이라는 실제 로봇 제어 파이프라인을 처음부터 끝까지 구축·디버깅)

## 하드웨어 (robot, sensors, actuators, compute board, prices if stated)
- XGO mini 로봇: 바퀴 달린 소형 로봇(위험 부담이 낮고 로봇 자체 손상 위험도 낮음), 팔(어깨/팔꿈치/그리퍼), 전방 카메라 + 측면 Logitech 웹캠(물리적으로 자주 빠짐 — 이번 영상에서도 아이가 뽑아놔서 오프라인으로 표시됨).
- GPU는 3장 체제(이전 영상에서 1장 사망)로 TP3, NVFP4 양자화 조합 — prefill이 느려지는 문제 언급. 과거 4장일 때는 다른 사람들이 메모리 오버클럭으로 500~600 tok/s까지 봤다고 하나, 본인은 GPU 온도 센서 부재를 이유로 오버클럭을 꺼림.
- 비전 추론 프레임레이트: 목표 2~3 FPS였으나 실제로는 토큰 생성 속도(추적 물체당 약 100~150ms 추가) 및 로봇 자체의 카메라 프레임 전송 병목 때문에 2 FPS에 못 미침.

## 소프트웨어 스택 (OS, SDKs, frameworks, models, languages, sim tools)
- 코딩 하니스 "OM"(정체 불확실, 06/05 영상과 동일 도구로 추정)을 음성 입력(Whisper 기반 소형 STT 모델, Cmd+B 녹음/Cmd+T TTS 단축키, Linux 시작 시 자동 실행)으로 조작.
- VLM 서버가 GLM 5.3 Flash를 호스팅, reasoning effort 파라미터(low/high, "max"/"extra high"는 내부적으로 high로 처리되는 것으로 추정 — 정확한 동작은 불확실)를 조절해 지연시간 최적화.
- 물체 인식은 구조화 JSON 출력(라벨 + XYXY bounding box + confidence + 선택적 note)으로 받아 OpenCV로 시각화, 그 좌표로 로봇 SDK 호출.
- 로봇의 저수준 동작(전진/회전/팔 관절 이동/그리퍼)은 규칙 기반(하드코딩된) SDK 프리미티브로 유지 — GLM53 Flash는 "어떤 프리미티브를 언제 호출할지"만 결정.

## 만드는 과정 — 순서대로 (what he tried first, next, ... in chronological order; the actual workflow)
1. 새 프로젝트 디렉토리를 만들고 OM 세션을 시작, 이전 영상의 규칙 기반(HSV 마스킹 + 하드코딩된 회전/중앙정렬 로직) 코드를 function calling 구조로 바꿔달라고 요청.
2. 먼저 비전(물체 인식) 디버그 뷰만 구축 — 초록 큐브에 대해 실시간 bounding box 오버레이를 확인, JSON 스키마(좌상단/우하단 좌표 + confidence)가 올바른지 검증.
3. 첫 요청이 약 17초나 걸리는 것을 발견(캐시/prefill 미스로 추정) → 재요청 시 600~985ms로 단축. "low" reasoning effort로도 물체 인식엔 충분하다고 판단, "high"는 불필요한 지연만 추가.
4. 전방 카메라가 검은 화면, 측면 Logitech가 오프라인으로 표시되는 문제를 디버깅 — 결국 모델/코드 문제가 아니라 케이블이 물리적으로 빠진 것이 원인(아이가 건드림).
5. 추적 대상 물체를 "wood wall", "computer fans" 등으로 늘려가며 확장성 테스트 — 예상과 달리 물체 1개 추가당 약 100~150ms씩 지연이 늘어남을 발견, 원인을 분석해보니 비전 타워 자체의 비용이 아니라 출력 JSON 토큰 수 증가(3장 GPU 기준 ~150 tok/s에서 물체당 약 15토큰 추가 생성)에 따른 디코딩 시간 증가로 결론.
6. 감지 루프가 응답 즉시("ASAP") 재요청하지 않고 매 1.1초마다만 폴링하던 버그, 그리고 "cube detector" 토글을 별도로 켜야만 파이프라인이 동작하던 숨은 의존성 버그를 발견해 수정.
7. confidence threshold(약 80%)를 추가 — 모델이 물체가 없어도 항상 뭔가를 감지했다고 출력하는 false positive 경향을 억제.
8. 마지막으로 규칙 기반 로직을 전부 제거하고, "큐브를 찾아서 집어라"는 완전 자율 루프로 전환 — GLM53 Flash가 회전/전진/그립 결정을 전부 담당, SDK 프리미티브만 고정.
9. 실행 중 팔꿈치 관절이 무작위로 씰룩이는 현상, "전진(roll forward)" 명령이 반복적으로 HTTP 409로 거부되며 수십 초씩 낭비되는 현상, 결정과 실제 실행 사이의 지연 등을 실시간으로 관찰하며 모델(OM)에게 자신의 로그를 읽고 원인을 스스로 진단·수정하게 요청.
10. 첫 시도는 큐브가 비스듬히 놓여 있어 그립 후 미끄러져 실패, 큐브를 정렬한 뒤 재시도해 성공(찾기→중앙정렬→접근→그립→들어올리기까지 전 과정 완주).

## 막힌 곳과 해결법 (failures, bugs, surprises, and how he debugged or worked around them)
- 카메라 "오프라인" 표시 → 실제로는 케이블이 물리적으로 빠진 것이었고 모델/코드와 무관 (직접 눈으로 확인 후 해프닝으로 처리).
- 물체 추적 개수를 늘릴수록 예상외로 지연이 커짐(개당 ~100~150ms) → 원인을 "비전 처리 비용"이 아니라 "출력 토큰 수 증가에 따른 디코딩 시간"으로 재규명, 본인이 이전에 가정했던 "물체 추가는 거의 공짜"라는 통념을 스스로 정정.
- 감지 루프 폴링 주기가 목표(즉시 재요청)와 다르게 동작 → OM에게 "ASAP"로 명시적으로 수정 요청해 해결.
- 숨겨진 "cube detector" 토글을 켜지 않아 파이프라인이 전혀 동작하지 않았던 문제 → 직접 찾아서 켬.
- 로봇이 "전진" 명령을 반복적으로 409(거부)로 되돌려받으며 시간을 낭비 → 정확한 거부 원인은 자막상 명확히 설명되지 않음, OM이 로그를 분석해 원인을 찾아 수정했다고 주장하나 세부 메커니즘은 불명.
- 그립 후 "들어올리기(lift)" 단계가 가끔 생략되거나 크게 지연 → 별도로 "grab-and-lift 함수가 실제로 lift를 수행하는지" 확인 요청, 명확한 근본 원인은 밝혀지지 않음.

## 수업 개념과 연결 (any link to KF / PF / PID / SLAM / localization / path planning / control loops / RL; write "없음" if none — do not invent links)
- 없음(공식적인 KF/PF/PID/SLAM 기법은 등장하지 않음). 다만 "카메라로 보고 → 중앙 정렬 → 접근 → 그립"이라는 반복 루프는 개념적으로 시각 서보잉(visual servoing)/폐루프 피드백과 유사한 발상이라는 점만 참고할 만함 — 수업에서 배우는 구체적 필터/제어기와는 무관.

## Paul의 Hardware Challenge에 주는 교훈 (concrete, 2–5 bullets)
- 이 영상은 "카메라 → VLM 추론 → 구조화 출력(JSON) → SDK 프리미티브 실행"이라는 LLM-로봇 제어의 실제 인터페이스 패턴을 가장 구체적으로 보여줌 — 다만 이는 GPU 3장(RTX Pro 6000)에서 150~200 tok/s로 돌아가는 파이프라인이라, Jetson Orin Nano Super에서는 훨씬 작은 VLM(1~4B급, heavily quantized)으로도 이 정도 반응속도를 기대하기 어려움. Hardware Challenge에 VLM 기반 인식을 넣는다면 프레임레이트/지연을 매우 보수적으로 잡아야 함.
- 저수준 프리미티브(이동/관절 제어)는 규칙 기반으로 고정하고, LLM은 "어떤 프리미티브를 호출할지"만 결정하게 한 설계는 좋은 참고 템플릿 — Paul의 KF/PF/PID/SLAM 구현도 이런 식으로 "결정론적 제어/필터 코드"는 그대로 두고, 상위 계획(있다면)만 별도 레이어로 분리하는 것이 안전.
- 물체 개수 증가에 따라 토큰 생성량이 늘어 지연이 커진다는 발견은, 저사양 보드에서 프롬프트/출력 스키마를 최소화하는 것이 지연 단축에 직결된다는 실용적 교훈 — Jetson에서 뭔가 유사한 구조를 시도한다면 출력 필드를 최소화할 것.
- 409 거부로 수십 초씩 낭비되는 장면은, 액추에이터/SDK 명령 인터페이스가 실패를 명확하고 빠르게 알려주는 것이 전체 루프 안정성에 중요하다는 것을 보여줌 — Paul이 로봇 SDK/드라이버를 다룰 때도 에러를 조용히 삼키지 않고 즉시 드러나게 설계/로깅하는 것이 디버깅 시간을 줄여줌.
- confidence threshold로 false positive를 거르는 방식은, 센서/인식 출력을 그대로 신뢰하지 않고 검증 단계를 두는 습관의 좋은 예 — Kalman/Particle Filter에서 관측치의 불확실성을 다루는 것과 발상은 다르지만, "출력을 곧이곧대로 믿지 않는다"는 원칙은 공유됨.

- "409" 오류의 정확한 발생 원인(로봇 SDK가 왜 전진 명령을 거부했는지)은 자막에서 명확히 설명되지 않아 불확실.

- reasoning effort 파라미터의 "max"/"extra high"가 실제로 서버에서 어떻게 처리되는지(내부적으로 "high"로 취급된다는 발표자의 추정)는 확정적이지 않음 — 불확실.
