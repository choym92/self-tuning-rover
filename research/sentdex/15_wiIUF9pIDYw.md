# 15 — Reinforcement learning with Unitree G1 humanoid (Dev w/ G1 P.5)
- 한 줄 요약: PPO로 학습한 아주 작은(2x64) 팔(arm) 타겟 추적 policy를 G1 실기에 라이브로 올려서 시연하고, reward 설계·training curve·팔이 멈춰버리는 현상 등을 리뷰하는 영상.
- 로봇 관련성: 높음

## 하드웨어
- Unitree G1 (닉네임 Jeff), 팔(arm) 전체 joint 제어. 손이 하나는 원래 고장(DOA)이라 새 손을 아직 교체 안 함.
- 리모컨(remote)을 물리 E-stop 겸 "로봇을 알려진 자세로 부팅시키는 절차"로 사용 — 리모컨을 항상 켜두게 강제하는 용도로도 활용.
- 모델 파일 용량: 초반엔 "184 kilobytes", 후반엔 "150 kilobytes 정도"라고 다르게 언급됨 — 정확한 수치는 불확실.

## 소프트웨어 스택
- 알고리즘: PPO (자막엔 "PO"로 나오지만 문맥상 PPO), stable-baselines3 사용.
- 네트워크 구조: 2x64의 아주 작은 MLP policy.
- OpenAI Gym 스타일 환경 포맷 사용(action → next observation/reward/done/info).
- 시뮬레이터: 실제 G1 조작 중 화면에 동시에 시뮬레이션된 G1도 매핑해서 보여줌(정확한 시뮬레이터 명칭은 이 영상에서 특정되지 않음).
- 타겟 위치 결정 로직/에피소드 타임아웃을 "codeex and 03"(자막 그대로, 추정상 OpenAI의 Codex와 o3 모델)이 제안해서 구현했다고 언급.
- GitHub의 "G1 vibes" 저장소, "RL shenanigans" 디렉터리에 코드 업로드 예정/일부 업로드. 살짝 수정된 Unitree SDK가 필요하다고 언급.

## 만드는 과정 — 순서대로
1. 팔(arm)이 현재 joint 위치 기준으로 3D 공간상의 목표 지점(타겟)을 찾아가는 policy를 목표로 설정. 목표 지점은 사람이 키보드(상/하/좌/우/앞/뒤)로 이동시킴 — 실제 손 위치를 공간상에서 직접 조작하는 추상화 레이어.
2. Observation space 설계: 총 24개 값 = 팔 joint 각도 7개 + joint 속도 7개(=14) + 손의 XYZ 위치 3개 + 목표 XYZ 위치 3개 + 현재-목표 delta 벡터 3개 + 에피소드 진행률(step fraction) 1개.
3. Action space 설계: 7차원 벡터, 매 스텝마다 각 joint에 주는 incremental(증분) 명령.
4. 에피소드 종료 조건 설계: 목표 도달(손이 목표에서 2cm 이내 — 튜닝 가능), self-collision(자기 몸통과 충돌), joint limit 도달, 그리고 delta 거리 기반으로 동적으로 계산되는 타임아웃.
5. Reward 설계: 목표 도달 시 +1.0, 충돌 시 -1.0, joint limit 도달 시 -0.5, 매 스텝 거리 기반 페널티, 그리고 손이 지면과 평행/손가락이 지면과 수직이 되도록 하는 자세(pose) 정규화 보너스(그립 자세 유지 목적)를 추가.
6. 여러 모델을 학습(약 24시간 소요)했고, 두 가지를 비교: 손목(wrist)을 타겟으로 삼은 모델(빨강)과 손바닥(palm)을 타겟으로 삼은 모델(초록) — palm 기준이 더 나은 결과.
7. 학습 도중 policy loss가 다시 올라가는 지점에서 학습을 중단. value loss는 계속 잘 내려가고 있었음.
8. 실기(G1)에 라이브로 policy를 올려 키보드로 목표를 이동시키며 시연. 느린 속도(pulling rate, half speed)로 시작 후 점차 속도를 올림(최대 pulling rate 5ms까지).
9. 속도를 올리다가 팔이 갑자기 멈추는(dampening) 현상 발생 → 재부팅으로만 복구 가능함을 확인.

## 막힌 곳과 해결법
- 손이 항상 물체를 잡기 좋은 자세(손바닥 평행, 손가락 수직)를 유지하도록 정규화를 넣었지만 충분하지 않았음 — RL reward 튜닝이 "fiddly"(까다로움)하다고 토로. 정규화 덕분에 완전히 없을 때보다는 손목이 나아졌지만 완벽하진 않음.
- 특정 joint가 목표 위치에 오래 도달하지 못하면 팔 전체가 멈춰버리는(주는, give up) 현상 발생 — 어느 모터가 원인인지 특정하지 못함. 유일한 해결법은 로봇 재부팅.
- 이전(구) policy는 팔꿈치가 바깥으로 나갔다가 다시 안으로 들어와야 하는 전환 동작을 특히 못했음(그 반대도 마찬가지) — 이번 PPO policy는 수백만 샘플 덕분에 훨씬 개선.
- 속도를 올릴수록(특히 5ms rate) 실기 동작이 매우 빨라지고 위험해짐 — 로봇을 "화나게"(joint limit 근처로 계속 밀어붙이면) 만들면 멈춰버릴 수 있다고 경험적으로 설명.
- 학습 도중 policy loss가 재상승하는 원인은 명확히 규명하지 못함(learning rate 문제일 수 있다고 추정만 함, 시청자에게 RL 전문가 의견을 구함).
- (본편과 별개 에피소드) 커뮤니티에서 공유된 영상: 최신 펌웨어에서 damp 모드(L1A 버튼)가 더 이상 즉각적이지 않아서 사람이 팔에 다칠 뻔한 사고 — 본인 시뮬레이터에서도 "로봇을 세워라" 명령 시 팔이 순간적으로 매우 빠르게 튕기는 것을 직접 재현해서 보여줌. 소프트웨어 상의 속도 제한과 SDK 자체의 기본 속도는 별개라는 점을 강조.

## 수업 개념과 연결
없음 — 이 영상은 PPO 기반 model-free RL로 진행되며, KF/PF/PID/SLAM/경로계획 등 수업에서 다루는 고전 알고리즘과 직접적인 연결점은 나오지 않음. (다만 "joint position을 목표로 계속 좁혀나가는" 구조는 넓게 보면 제어 루프와 유사하지만, 영상에서 PID/제어이론 언어로 설명되지 않으므로 억지 연결은 하지 않음.)

## Paul의 Hardware Challenge에 주는 교훈
- 아주 작은 신경망(2x64, 100~200KB급)으로도 실제 로봇 팔 제어가 가능했다는 점 — Hardware Challenge용 온보드 연산량은 생각보다 가벼울 수 있음(무거운 보드가 꼭 필요하지 않을 수도).
- Sim-to-real을 하기 전에 시뮬레이션과 실기 간 joint 매핑이 충분히 정확한지 먼저 확인하는 과정이 필수적이었음 — 작은 하드웨어라도 센서/액추에이터 좌표계 검증을 먼저 하는 습관이 중요.
- 물리 E-stop(리모컨)을 "부팅 절차에 강제로 포함"시켜서 항상 켜두게 만든 아이디어는, 안전장치를 우회 불가능하게 워크플로우에 심는 좋은 설계 패턴.
- Reward shaping은 예상보다 훨씬 반복적/실험적(trial-and-error)임 — 마감(12/10)을 고려하면 reward 튜닝에 넉넉한 시간을 배정해야 함.
- 액추에이터가 limit에 오래 부딪히면 하드웨어 보호 로직(damp/shutdown)이 발동해 재부팅이 필요해질 수 있다는 점 — 실기 테스트 세션 시간을 예상보다 넉넉히 잡을 것.
