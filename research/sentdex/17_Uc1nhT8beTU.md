# 17 — Moving the arms/hands (P.3)

- 한 줄 요약: SDK가 팔의 Cartesian(직교좌표) 제어를 지원하지 않아, RL/IK 대신 사람이 직접 팔을 잡고 방향별로 시범을 보여 라벨링한 데이터(방향당 약 50개)로 작은 회귀 신경망을 학습시켜 "그럭저럭 쓸만한" 손 이동 제어를 구현.
- 로봇 관련성: 높음

## 하드웨어 (robot, sensors, actuators, compute board, prices if stated)
- 팔 1개당 모터 7개(자막: "seven different motors"), 각각 다른 축으로 회전하며 서로 영향을 줘서 직교좌표 변환이 어렵다고 설명.
- 리모컨(remote controller)을 이번 영상에서 처음 손에 넣음 — L1+A 버튼 조합으로 로봇을 damp(감쇠/무력화) 상태로 만드는 비상정지(e-stop) 기능을 확인 및 시연, 로봇 본체 배터리보다 리모컨 배터리 수명이 더 길어 상시 켜둠. 빨간 테이프로 버튼 표시.
- SDK 상 arm 제어 topic을 점유해도 허리(waist) 위쪽만 제어권을 가져가며, 다리는 계속 독립적으로 균형 유지("topic" 단위로 소유권이 나뉘는 구조).
- 가격 관련 언급 없음(이전 영상들과 동일 로봇, 새 가격 정보 없음).

## 소프트웨어 스택 (OS, SDKs, frameworks, models, languages, sim tools)
- 모델: scikit-learn MLPRegressor, hidden layer 2개(각 32 뉴런), 활성함수 ReLU(자막상 본인도 "아마 relu일 것"이라며 약간 확신 부족), Adam optimizer(자막 "atom", 확실친 않음), 출력층 선형, 손실함수 MSE, 60 epoch 학습. GPU 없이 CPU로 학습.
- 데이터 수집 도구: `arm_train_recorder.py` — 3-2-1 카운트다운 후 "up/down/left/right/forward/backward" 중 하나를 음성으로 지시, 사람이 로봇 팔을 직접 잡고 그 방향으로 움직이면 시작/종료 시점의 관절 각도(12개 관련 관절, waist 등 일부는 사용 안 함)를 direction 라벨과 함께 기록. 방향당 약 50개 샘플(최소치, 더 적어도 될 가능성 있다고 언급), 누적 데이터셋 약 1,700개.
- 시뮬레이터: G1용 URDF를 로드해 학습된 정책을 사전 검증하려 시도 (실물 투입 전 안전 확인 목적).
- LLM 도구: 계속 OpenAI o3(자막 "03")를 코딩 파트너로 사용. GUI(팔 관절값 확인용 arm GUI 등)도 LLM에게 요청해 빠르게 제작.
- GitHub: 이번 영상에서 일부 코드/파일을 처음 공개 업로드(서드파티 SDK인 RealSense, Livox, Unitree SDK는 직접 올리지 않고 링크만 제공). Unitree SDK는 수정이 필요해 fork 예정이라고 언급, 레포 구조(G1 전용 패키지로 통합할지)는 아직 미정.

## 만드는 과정 — 순서대로 (what he tried first, next, ... in chronological order; the actual workflow)
1. "부엌에서 물 한 병을 가져오는" 과제를 목표로 설정, 이동/SLAM/occupancy grid는 어느 정도 해결됐다고 보고 다음 단계로 손 제어를 고민.
2. Unitree SDK의 high-level arm 예제를 확인 → 기대와 달리 joint-level(관절 단위) 제어만 제공, Cartesian(XYZ) 제어는 노출되어 있지 않음을 발견.
3. 시뮬레이터+RL(보상함수 튜닝) 방식을 고려했으나, RL이 사실상 지도학습처럼 느껴지고 sim-to-real 문제도 우려되어 회피.
4. 대신 "로봇에게 직접 보여주면 어떨까"라는 아이디어로 전환 — 사람이 팔을 잡고 방향별 동작을 시범 보이며 관절 각도 데이터를 라벨링 수집(kinesthetic teaching/모방학습에 가까운 접근).
5. `arm_train_recorder.py`로 방향당 약 50개씩 데이터 수집(허리는 0으로 고정해 문제를 단순화).
6. scikit-learn MLP(2×32 은닉층)로 회귀 모델 학습, 학습/테스트 곡선 및 방향별 MSE 확인(60 epoch 이후 과적합 시작 관찰).
7. 실물 투입 전 안전을 위해 시뮬레이터(URDF 기반)에서 먼저 정책을 테스트 → 화살표 키로 상/하/좌/우 명령을 줬을 때 시뮬레이션에서는 방향이 맞지 않게 움직임(예: 위로 명령해도 안 올라감) → 그런데도 실물 로봇에서는 정상 동작 확인(관절 라벨/순서 불일치로 추정, 원인 미해결).
8. 실물에 정책 배포: 안전을 위해 목표 위치로 "급하게 점프"하지 않고 서서히 보간(gradient)하도록 구현 — 팔 모터가 매우 빠르고 강력해서 급격한 명령은 사람이 다칠 수 있다고 강조.
9. 학습된 정책으로 실제 손을 상/하/좌/우/전/후로 이동시키는 데모 성공, 완벽하진 않지만 "물체 방향으로 충분히 유도 가능한 수준"이라고 평가.
10. 기타 개선사항 정리: occupancy grid의 "유령 픽셀 궤적" 버그 수정(LiDAR 높이 근처 포인트 필터링 추가), 이전 영상의 이중 반전(double-flip) occupancy grid 버그 수정, 배터리 퍼센트 표시는 SDK에 아예 없음을 확인(포기), 걷는 속도를 Shift 키로 빠르게 전환 가능하게 추가, 리모컨 e-stop 기능 확인.

## 막힌 곳과 해결법 (failures, bugs, surprises, and how he debugged or worked around them)
- **SDK가 Cartesian 손 제어를 지원하지 않음** — high-level 예제를 열어보고 나서야 joint-level뿐임을 확인, 접근 방식을 RL/IK 대신 모방학습형 회귀로 전환.
- **RL+sim 경로는 의도적으로 회피** — 보상함수 튜닝의 "사실상 지도학습" 성격과 sim-to-real 리스크를 이유로 채택하지 않음(구현 시도 자체를 안 함, 판단으로 회피).
- **시뮬레이터에서 정책이 이상하게 동작(실물과 다름)** — 관절 라벨/순서가 URDF와 실물 간 다를 가능성으로 추정했지만 원인을 끝까지 규명하지 못함, "더 살펴봐야 한다"로 마무리(향후 RL/sim 전이 시 걸림돌로 남을 것으로 예상).
- **팔 명령의 기본 이동 속도가 매우 빠르고 위험** — 급하게 목표 자세로 명령을 보내면 손목 등을 다치게 할 수 있음을 인지하고, 모든 새 목표 자세는 부드러운 gradient(점진적 보간)로 이동하도록 구현해 해결.
- **배터리 퍼센트를 SDK에서 읽을 수 없음** — 전압이라도 읽어 계산하려 했으나 옵션 자체가 없어 포기(미해결 한계로 기록).
- **occupancy grid 유령 궤적 버그** — 로봇이 걸을 때 LiDAR 유닛 높이 근처의 포인트가 계속 잔상처럼 남는 문제, 해당 높이/거리 범위의 포인트를 필터링하는 방식으로 해결.
- **occupancy grid 이중 반전 버그** — 이전 영상에서 LiDAR가 원래 거꾸로 장착되어 한 번 반전 처리했는데, o3가 이미 반전된 데이터를 실수로 한 번 더 반전시켜 지도가 잘못 나왔던 문제를 이번에 수정.

## 수업 개념과 연결 (any link to KF / PF / PID / SLAM / localization / path planning / control loops / RL; write "없음" if none — do not invent links)
없음(직접적 KF/PF/PID/SLAM 구현 없음). 다만 참고할 점: 영상 초반에 RL(강화학습)을 명시적으로 고려했다가 "보상함수 튜닝이 사실상 지도학습처럼 느껴진다"는 이유와 sim-to-real 문제 우려로 의도적으로 포기하고, 대신 모방학습(사람이 직접 시연한 데이터를 라벨로 쓰는 지도학습형 회귀)을 택했다는 점은 수업에서 다루는 "제어 vs 학습 기반 접근"의 실전 트레이드오프 사례로 참고할 만하나, 이것이 course algorithm(KF/PF/PID/SLAM/search)에 해당하지는 않음.

## Paul의 Hardware Challenge에 주는 교훈 (concrete, 2–5 bullets)
- **모방학습(사람이 직접 시범 → 소량 데이터로 회귀 모델 학습)은 IK/RL을 우회하는 실전적인 "빠른 해법"** — 다만 이 방식 자체는 Hardware Challenge가 요구하는 "코스 알고리즘(KF/PF/PID/SLAM/search+smoothing) 구현" 요건을 충족하지 못하므로, Paul은 이런 임기응변형 접근과 과제 요건용 알고리즘을 구분해서 계획해야 함.
- **액추에이터 안전: 목표 위치로 급격히 점프하지 말고 항상 점진적으로 보간(ramp/gradient)할 것** — PID의 setpoint 변화를 부드럽게 주는 것과 같은 원리이며, Paul의 챌린지 플랫폼에서 서보/모터를 다룰 때 일반적으로 적용 가능한 안전 수칙.
- **시뮬레이터-실물 간 관절/좌표 정의 불일치는 흔한 함정** — URDF 기반 시뮬레이션 결과가 실물과 다르게 나온 사례처럼, Paul이 시뮬레이션에서 먼저 검증할 계획이라면 좌표계·관절 순서를 명시적으로 맞춰보는 검증 단계를 넣을 것.
- **벤더 SDK가 기대하는 센서 값(예: 배터리 퍼센트)을 항상 제공하진 않음** — 플랫폼(Freenove/XGO/Jetson) 선택 전에 실제로 어떤 텔레메트리/센서 값을 코드로 읽을 수 있는지 초기에 검증해둘 것.
- **물리적 비상정지(e-stop) 수단을 마련하는 것이 실전에서 중요** — 리모컨의 damp 버튼처럼, Paul의 챌린지 하드웨어에도 소프트웨어 오작동 시 즉시 멈출 수 있는 물리적/하드웨어적 수단을 준비할 것.
